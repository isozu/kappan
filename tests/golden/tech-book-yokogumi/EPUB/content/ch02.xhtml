第2章 分散システムの設計原則

分散システムは単一マシン上のプログラムとは 本質的ほんしつてきに異なる難しさを抱える。 本章では、分散システム設計における基本原則を取り上げる。

本章は 第1章 で扱ったネットワーク基礎を踏まえ、分断耐性を中心に論じる。

2.1 CAP 定理

CAP定理は分散システムの設計上、次の 3 つの性質を同時には満たせないと述べている。

  • C (Consistency)：一貫性
  • A (Availability)：可用性
  • P (Partition tolerance)：ネットワーク分断耐性

ネットワーク分断は実世界で発生するため、現実的な選択肢は CP か AP のどちらかになる。

図2.1に示した構造は、Kappan のような書籍ビルダにとっても示唆深い。 ローカルマシン上で完結する Kappan は本質的に CP 側だが、分散ビルド（M3 想定）を 扱う場合は AP との折り合いが必要になる1。

2.2 一貫性モデル

一貫性は単一の概念ではなく、強い〜弱いのスペクトルで語られる。

モデル 強さ 代表例
線形化可能性 強 単一マスター DB
順序整合性 中 Lamport clock
因果整合性 中 Vector clock
結果整合性 弱 DNS, S3

上表で示した通り、一貫性モデルの選択肢は多い。

可用性の定量化には、稼働率 AA を用いる。

A=MTBFMTBF+MTTRA = \frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}}

式2.1のように、平均故障間隔（MTBF）が長く平均修復時間（MTTR）が 短いほど可用性は高くなる。

interface CausalOrder<T> {
  apply(event: T, vectorClock: VectorClock): void;
  query(): readonly="readonly" T[];
}

class VectorClock {
  private clocks: Map<NodeId, number> = new Map();
  bump(node: NodeId): void {
    this.clocks.set(node, (this.clocks.get(node) ?? 0) + 1);
  }
}

リスト2.1はベクトルクロックの簡略実装である。

2.3 障害モデル

分散システムでは「正常」と「障害」が連続的に存在する。

  1. クラッシュ障害：ノードが停止する
  2. 省略障害：メッセージが失われる
  3. タイミング障害：応答が遅延する
  4. ビザンチン障害：任意の挙動を取る

ビザンチン障害は最も扱いにくく、一貫性モデルの選択も再考が必要になる。
