第4章 実装パターン

本章では、典型的てんけいてきな実装パターンを扱う。設計と実装の境界きょうかいは曖昧だが、 ここでは コードに落ちる粒度のパターンに絞って論じる。

4.1 サーキットブレーカー

サーキットブレーカーは、外部依存への呼び出しが連続失敗した場合に 回路を「開く」ことで雪崩的障害を防ぐパターンである。

class CircuitBreaker {
  private state: 'closed' | 'open' | 'half-open' = 'closed';
  private failureCount = 0;
  private openedAt = 0;

  async="async" call<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === 'open') {
      if (Date.now() - this.openedAt > this.config.resetTimeout) {
        this.state = 'half-open';
      } else {
        throw new Error('circuit open');
      }
    }
    try {
      const v = await fn();
      this.failureCount = 0;
      this.state = 'closed';
      return v;
    } catch (err) {
      this.failureCount++;
      if (this.failureCount >= this.config.threshold) {
        this.state = 'open';
        this.openedAt = Date.now();
      }
      throw err;
    }
  }
}

リスト4.1（[@lst:circuit-breaker]）は最小実装のサーキットブレーカ。

4.2 バルクヘッド

バルクヘッドは「ある障害が他の正常な処理を{巻き込まない}」ように リソースプールを分離するパターンである。

観点 バルクヘッドなし バルクヘッドあり
障害の伝播 全域 区画内
リソース効率 高い やや低い
観測のしやすさ 低い 高い

表4.1（[@tbl:bulkhead]）の通り、バルクヘッドは効率を多少犠牲にして 障害の影響範囲を最小化する。

4.3 リトライとバックオフ

リトライは諸刃の剣である。素朴な「即時リトライ」は障害を増幅させかねない。

  • 指数バックオフ：1s, 2s, 4s, 8s, ...
  • ジッタ付き指数バックオフ：分散させる
  • リトライ予算：単位時間あたりのリトライ回数上限

図4.1に示したように、ジッタを入れないと同期再試行による スパイクが発生する1。

4.4 アイドルタイムアウト

接続は永遠には維持できない。アイドルタイムアウトは、 使われていない接続を解放するための仕組みである。

タイムアウトを設定しないシステムは、いつかリソース枯渇で停止する。

— 運用エンジニアの経験則

実装では、各層（クライアント、ロードバランサ、プロキシ、サーバ）で タイムアウトを揃える必要がある。揃わないと末端側のタイムアウトが 他のレイヤを巻き込んで失敗する。
