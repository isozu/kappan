第3章 プロトコル比較

本章では、現代の 主要しゅような通信プロトコルを比較する。実務での選定では、 要件の優先順位を明確にしないと客観的な判断ができない。

3.1 HTTP/1.1 と HTTP/2 と HTTP/3

3 つの HTTP バージョンは、それぞれ異なる課題を解決するために生まれた。

  • HTTP/1.1：人間が読めるテキストベース。1 接続 1 リクエストが基本
  • HTTP/2：バイナリフレーミングと多重化。1 接続で並列リクエスト
  • HTTP/3：トランスポートを QUIC に置換。ヘッドオブラインブロッキングを根絶
バージョン トランスポート ヘッダ圧縮 サーバープッシュ
HTTP/1.1 TCP なし なし
HTTP/2 TCP HPACK あり
HTTP/3 QUIC (UDP) QPACK あり

3.2 gRPC

gRPC は HTTP/2 上のバイナリ RPC プロトコルである。Protocol Buffers を IDL として スキーマ駆動で API を定義する。

service BookService {
  rpc GetBook(GetBookRequest) returns (Book);
  rpc ListBooks(ListBooksRequest) returns (stream Book);
}

message Book {
  string id = 1;
  string title = 2;
  repeated string authors = 3;
}

リスト3.1（[@lst:grpc-proto]）は典型的な protobuf 定義。

サーバストリーミングと双方向ストリーミングが標準で扱えるため、リアルタイム性の 要件があるシステムでは有力な選択肢になる1。

3.3 WebSocket

WebSocket は HTTP の Upgrade ハンドシェイク後に双方向の TCP コネクションを開く。

const ws = new WebSocket('wss://example.com/feed');
ws.addEventListener('message', (e) => {
  const msg = JSON.parse(e.data);
  handleEvent(msg);
});
ws.send(JSON.stringify({ type: 'subscribe', channel: 'ticks' }));

リスト3.2 のように API は単純で、ブラウザ／Node 両方で同じ感覚で扱える。

WebSocket は「常時接続」のためのプロトコルであり、リクエスト／レスポンスを モデル化したい場合は素直に HTTP を使う方がよい。

3.4 プロトコル選定の指針

選定では次の軸を検討する。

  1. 双方向性が必要か（必要なら WebSocket / gRPC streaming）
  2. 強い型定義が必要か（必要なら gRPC）
  3. ブラウザ直対応が必要か（必要なら HTTP / WebSocket）
  4. 帯域効率が必要か（必要ならバイナリプロトコル）

これらの組み合わせで、HTTP/3 + gRPC のようなハイブリッド構成も増えてきた。
